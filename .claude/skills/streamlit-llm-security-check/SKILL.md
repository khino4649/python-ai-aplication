# Streamlit + LLM アプリのセキュリティチェック

Streamlit アプリは「サーバー上の Python がそのまま UI になる」ため、普通の Web アプリとは違う落とし穴がある（ウィジェットの値はすべてブラウザに送られる、インポートしたモジュールの変数は全ユーザーで共有される、既定では認証がない、など）。そこに LLM API が加わると、API キーと利用料、プロンプトインジェクション、LLM 出力の扱いという別の論点が乗る。このスキルは両方の観点でアプリを点検し、レポートにまとめる。

目的は「実際に起こりうる被害」を開発者に伝えること。チェックリストを機械的に埋めることではない。誤検知を並べるとレポートが信用されなくなるので、根拠を確認できたものだけを指摘として書く。

## 進め方

### 1. 前提を把握する

最初にアプリの全体像と**利用形態**をつかむ。深刻度は利用形態で大きく変わるからだ（ローカルで自分だけが使うアプリと、URL を知っていれば誰でも使える公開アプリでは、「認証がない」の重みがまったく違う）。

- エントリーポイント（`streamlit run` の対象）、モジュール構成、使っている LLM SDK
- 利用形態の手がかり: README、`Dockerfile`、`.streamlit/config.toml`、`Procfile`、デプロイ設定、CLAUDE.md の記述
- API キーの持ち方: サーバー側の `.env` / `st.secrets` か、ユーザーが自分で入力するか
- LLM がツール呼び出し（function calling）やコード実行、外部アクセスをするか

利用形態がわからなければ、ユーザーには聞かずに「インターネットに公開された場合」を基準に評価する。そのうえで、ローカル限定ならどの指摘の深刻度が下がるかをレポートに書く。

### 2. 補助スクリプトで候補を洗い出す

```bash
python <このスキルのディレクトリ>/scripts/scan.py <対象プロジェクトのディレクトリ>
```

標準ライブラリだけで動き、`.venv` などは除外する。秘密情報らしき文字列、`unsafe_allow_html=True`、`eval`/`exec`、パスワード欄の初期値、モジュールレベルの可変オブジェクト、`config.toml` の危険な設定、`.gitignore` の漏れなどを `file:line` つきで一覧にする。

出てくるのは**手がかりであって指摘ではない**。ヒットしたら必ずコードを読み、実際に問題になるかを判断すること。逆に、スクリプトが拾えない問題（ロジックの欠陥、プロンプトの組み立て方など）のほうが重要なことも多い。

### 3. コードを読んで観点ごとに確認する

`references/checklist.md` を読み、各観点に沿ってコードを確認する。小規模なアプリ（数ファイル程度）なら、アプリ本体の `.py` はすべて通読する。Streamlit の問題はファイルをまたいで起きることが多いからだ（例: `tools.py` で組み立てたプロンプトを `app.py` が描画する）。

主な観点（詳細と修正例は checklist.md にある）:

1. 秘密情報の管理（API キーのハードコード、Git への混入、ブラウザへの送信、ログやエラー表示）
2. アクセス制御と利用料の悪用（認証、レート制限、入力・出力長の上限）
3. プロンプトインジェクション（信頼できない入力の混入、システム指示の分離）
4. LLM 出力の扱い（HTML 描画、Markdown 画像やリンクによる情報持ち出し、コード実行）
5. 過剰な権限（ツール呼び出し、ファイル操作、外部アクセス）
6. セッションとデータの分離（共有キャッシュ、モジュール変数、ログ）
7. ファイルアップロードと外部リソース（サイズ、形式、SSRF、パストラバーサル）
8. エラー表示と設定（`showErrorDetails`、XSRF/CORS、公開アドレス）
9. 依存関係（バージョン固定、既知の脆弱性）

依存関係の脆弱性は、`pip-audit` が入っていれば `python -m pip_audit -r requirements.txt` で確認する。入っていなければ勝手にインストールせず、「未確認」としてレポートに書き、手順を案内する。

Git リポジトリなら、秘密情報が過去のコミットに入っていないかも確認する（`git log --all -p -- .env` や、キーの接頭辞での `git log -S`）。過去に一度でもコミットされたキーは、今のファイルから消しても漏えい済みとして扱う。

### 4. 深刻度を付ける

| 深刻度 | 目安 |
|---|---|
| 🔴 重大 | すぐに実害が出る。例: 公開リポジトリやブラウザに API キーが漏れている、LLM 出力を `exec` している |
| 🟠 高 | 条件がそろえば実害が出る。例: 認証なしの公開アプリがサーバーの API キーを使っている、LLM 出力を `unsafe_allow_html` で描画している |
| 🟡 中 | 被害は限定的だが対策すべき。例: 入力長の上限がない、例外の詳細がユーザーに見える |
| 🔵 低 | 多層防御として推奨。例: 依存バージョンが固定されていない |
| ⚪ 情報 | 問題ではないが知っておくべき前提や設計上の注意 |

深刻度は「起こりやすさ × 被害の大きさ」で付け、利用形態を必ず考慮する。指摘ごとに「どういう人が、何をすると、何が起きるか」を一文で書けないなら、その指摘は深刻度を下げるか「要確認」にする。

### 5. レポートを書く

レポートは対象プロジェクトのルートに `security-report-YYYY-MM-DD.md` として保存する（ユーザーが場所を指定したらそちら）。チャットには、総合評価と重大・高の指摘の要約、レポートのパスを返す。

レポートでは次のことを守る。

- **秘密情報の値は書かない。** キーを見つけたら `AIza****（末尾4文字: abcd）` のように伏せる。レポート自体が共有されることがあるからだ。
- **コードは修正しない。** このスキルの役割は診断と報告。修正案はレポートに書き、直すかどうかはユーザーが決める。
- 根拠は `file:line` で示し、該当コードを短く引用する。
- 「確認済み」の問題と「要確認」（判断に情報が足りないもの）を分ける。
- 良くできている点も書く。何を変えてはいけないかが伝わるからだ。

テンプレート:

```markdown
# セキュリティレポート: <アプリ名>

- 実施日: YYYY-MM-DD
- 対象: <パス>（<主要ファイル>）
- 構成: Streamlit <バージョン> / <LLM SDK とバージョン>
- 想定した利用形態: <例: ローカルでの個人利用（README より）。公開時の評価も併記>

## 総合評価

<2〜4 文。最も重要なリスクと、まず取るべき対応>

| 深刻度 | 件数 |
|---|---|
| 🔴 重大 | n |
| 🟠 高 | n |
| 🟡 中 | n |
| 🔵 低 | n |
| ⚪ 情報 | n |

## 指摘事項

### [H-1] <短いタイトル>

- **深刻度**: 🟠 高（ローカル限定なら 🔵 低）
- **分類**: <観点名> / <OWASP LLM Top 10 の該当項目があれば: 例 LLM10 Unbounded Consumption>
- **場所**: `app.py:52`
- **内容**: <何が問題か。該当コードの短い引用>
- **想定される被害**: <誰が・何をすると・何が起きるか>
- **修正案**: <具体的な直し方。必要なら短いコード例>

（重大 → 高 → 中 → 低 → 情報 の順に並べる。ID は C/H/M/L/I + 連番）

## 良い点

- <例: API キー入力欄が type="password" で、.env が .gitignore に含まれている>

## 未確認の項目

- <例: pip-audit が未インストールのため、依存関係の既知の脆弱性は未確認。`pip install pip-audit` 後に `python -m pip_audit -r requirements.txt` を実行>

## 対応の優先順位

1. <まず直すもの>
2. ...
```

指摘がゼロの観点は「指摘事項」に書かない。必要なら「良い点」で触れる。
